# aidea.docs-healthcheck — docs ヘルスチェック

プロジェクトの設計ドキュメントの健全性を一括で確認する**汎用スキル**。
具体的な対象ディレクトリ・規約・チェックコマンドなど**このリポジトリ固有の情報は、同じディレクトリの [`specifics.md`](./specifics.md) に分離**してある。

## 進め方

### 0. 固有情報の読み込み (必須)

まず同ディレクトリの **`specifics.md`** を読む。そこにこのリポジトリの以下が定義されている。

- 対象ディレクトリ (どの docs 群をチェックするか)
- 各領域のチェック基準の SSoT (README の「ヘルスチェック」節など)
- frontmatter 規約・配置ルールの SSoT
- 実装詳細禁止チェックの具体コマンド

`specifics.md` が無いリポジトリでは、`docs/` 配下の README / LAYOUT 等から規約を推測し、下記の汎用カテゴリで判定する。

### 1. 汎用チェックカテゴリ

`specifics.md` の指示に従いつつ、最低限以下を確認する。

- **矛盾**: ドキュメント同士／上位決定 (ADR 等) との食い違い。決定が優先、暫定・提案ステータスは指摘レベルを下げる
- **未定義参照**: 本文が言及するファイル・概念が存在しない／削除済みパスへの参照
- **stale (実装との乖離)**: コードと 1:1 対応すべき仕様が実装と食い違っていないか／コードにあるのに記載が無い機能
- **frontmatter 不整合**: 必須フィールド欠落・参照切れ・双方向リンクの非対称・空配列の省略・規約違反
- **抜け漏れ**: 横断的関心事 (永続化・ビュー階層など) への反映漏れ

### 2. 報告

- カテゴリ別に、**file:line / フラグ種別 / 問題の要点 / 修正提案** を列挙する
- 明確なものは修正提案、判断が要るものはユーザに問い合わせる
- 全カテゴリでフラグゼロなら**サイレント pass** (「問題なし」と短く報告)

## スコープ

- 引数・会話でスコープ指定があればその範囲のみ
- 指定が無ければ `git diff` で変更のあったドキュメント・コードを中心に、その参照／被参照も対象に含める

## 守ること

- フラグが立ったら**その PR 内で解消**する (別 PR に持ち越さない)
- 詳細な判定基準は必ず `specifics.md` と、そこが指す SSoT に従う (このファイルに基準を二重化しない)
