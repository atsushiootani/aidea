# aidea.issue.create

Aidea プロジェクトで GitHub issue を新規作成するための手順。**対話式に「あるべき状態」を中心に情報を整理**し、`/aidea.issue.start` が理解しやすい書式で投稿する。

引数 `$ARGUMENTS` には issue の概要やタイトル候補を渡してもよい (空でもよい)。

## やること

### 1. 出発点の確認

- **引数あり**: 概要 / タイトル候補として扱い、これに肉付けする旨をユーザに示す
- **引数なし**: 「どんな機能追加 / 不具合修正を issue にしたい？」と対話を開始する

### 2. 種別の判定 (feature / bug)

ユーザに「これは **新しい機能・改善 (feature)** か、**不具合修正 (bug)** どちらか」を確認する。
返答に応じて付与するラベルを以下のとおり確定する:

- feature → `enhancement`
- bug → `bug`

曖昧なら本文から推測し、ユーザに最終確認する。

### 3. 「あるべき状態」を引き出す (最重要)

完了条件として **「こうなっていれば終わり」** を具体化する。
曖昧な場合は以下の観点を 1 つずつ聞いて具体化する:

- 画面 / ボタン / コマンドはどう見えていて、どう動くか
- 入出力のデータや形式
- 使い手から見える挙動
- 受け入れ条件 (確認可能な基準)

**このセクションは必ず埋める。** `/aidea.issue.start` が feature/bug を問わず分岐判断の核として読む部分なので、曖昧さを残さない。

### 4. 補足情報を引き出す

以下を 1 つずつ聞く (相手にとって自明なら省略可能と明示する):

- **動機 / 背景**: なぜこうしたいか、何が不便か
- **現状** (不具合系のみ): 実際に起きていること、再現手順、影響範囲
- **スコープ**: 含むもの / 含まないもの (除外事項は特に重要)
- **参考**: 関連 specs / decisions / 既存 issue / スクショ / URL

### 5. タイトル案と本文ドラフトの提示

**タイトル** は 60 文字程度以内、動詞で終わる短い表現を提案する。
例:
- feature: `issue スキルを作る` / `GitDiff に Scene を追加する`
- bug: `Companion 再起動時に initialPrompt が送信されない`

**本文** は以下の書式で組み立てる。空セクションは省略してよい。

````markdown
# あるべき状態

(完了条件 / 期待される挙動。最重要セクション。箇条書きで可)

## 動機 / 背景

(なぜ必要か / 何が不便か)

## 現状 (不具合系のみ)

(実際の挙動 / 再現手順 / 影響範囲)

## スコープ

- 含むもの: ...
- 含まないもの: ...

## 参考

- 関連 specs: `docs/specs/...`
- 関連 issue: #NN
- その他: URL / スクショ
````

タイトル・本文・ラベル案をユーザに提示し、修正点があるか確認する。**ユーザの承認を得るまで次に進まない。**

### 6. issue 作成

`gh issue create --title "<タイトル>" --body "<本文>" --label "<ラベル>"` で作成する。

- 本文は **HEREDOC で渡してフォーマットを保つ**
- ラベルは手順 2 で決めた `enhancement` または `bug` を付ける。複数ラベル指定があれば `--label "bug" --label "<他>"` の形で追加する
- `--assignee @me` を付けて自分をアサインしておく (任意。ユーザ指示に従う)

例:

```bash
gh issue create \
  --title "issue スキルを作る" \
  --label "enhancement" \
  --assignee @me \
  --body "$(cat <<'EOF'
# あるべき状態

- ...

## 動機 / 背景

- ...
EOF
)"
```

### 7. 結果の報告

作成された issue の番号・タイトル・URL をユーザに表示する。
併せて「この issue に着手するなら `/aidea.issue.start <番号>` が使えるよ」と補足する。

## 注意

- 本文には **「あるべき状態」を必ず先頭に** 書く (`/aidea.issue.start` が最初に読むセクション)
- ラベルは最低限 `enhancement` か `bug` のどちらか **1 つを必ず付ける**
- ユーザの承認を得る前に `gh issue create` を実行しない
- 対話は **1 問ずつ**。複数の質問を一度に投げない
- 引数に機微情報 (トークン等) が含まれている場合は本文に載せない
