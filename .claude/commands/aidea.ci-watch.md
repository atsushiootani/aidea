# aidea.ci-watch

`aidea.ci-fix` を実行し、CI エラーが残っていれば 10 分待って繰り返すウォッチャー。**最大 3 回** 試行して、成功・諦め・上限到達のいずれかでユーザに報告して終了する。

引数 `$ARGUMENTS` に Companion 名 (例: `red-chan`) を指定すると、`aidea.ci-fix` の実行をその Companion にハンドオフし、結果のハンドオフバックを受けて次の判定に進む。

## 引数

- 引数なし: 自分自身で `aidea.ci-fix` を実行する (ローカルモード)
- 引数あり: 指定された Companion 名 (例: `red-chan`) に `aidea.ci-fix` をハンドオフする (委譲モード)
  - 利用可能な Companion 名は `.aidea/claude/aidea.md` の一覧を参照する

## 共通の前提

- 現在ブランチに対応する PR が存在することを前提とする (なければ最初に検出して停止)
- 「試行回数」は 1, 2, 3 のいずれか。最大 3 回で打ち切る
- 試行間の待機は **10 分 (600 秒)**

## ローカルモード (引数なし) のやること

### 1. 試行ループ (最大 3 回)

以下を最大 3 回繰り返す。

1. **CI 確認 & 修正**: `aidea.ci-fix` スキルを呼び出す
2. **結果判定** (ci-fix の報告内容から判断):
   - **CI 成功** (「CI は通過しています」): ループを抜けて成功報告へ
   - **進行中**: ループを抜けて進行中報告へ (ci-fix が修正をしていないため待っても変化しないことがある。ただし push 直後の再実行待ちの可能性もあるので、進行中であっても 10 分待って再確認は行う → 次の試行へ進む)
   - **修正して push 済み**: 次の試行に備えて待機へ
   - **修正不能 / 仕様変更要 / その他停止**: ループを抜けて諦め報告へ
3. **待機**: 試行回数が 3 未満かつ次の試行へ進む場合のみ、`sleep 600` で 10 分待機する
4. 試行回数を 1 増やして 1 に戻る

### 2. 終了報告

ループ終了の理由に応じて、以下のいずれかをユーザに報告する。

#### 2-A. CI 成功

```
✅ CI 通過を確認しました (試行 N/3 回目)。
<最後の ci-fix が報告した内容の要約>
```

#### 2-B. 諦め (修正不能)

```
⚠️ CI エラーを自動修正できませんでした (試行 N/3 回目)。
<ci-fix が報告した停止理由>

手動対応をお願いします。
```

#### 2-C. 上限到達

```
🛑 3 回試行しても CI 通過に至りませんでした。

## 試行履歴
1. <1 回目の結果概要>
2. <2 回目の結果概要>
3. <3 回目の結果概要>

手動対応をお願いします。
```

### 3. 次のアクション提案

終了報告の **直後に** 「次のアクション候補」を番号付きリストで提示し、ユーザが番号で選べるようにする。状況ごとに以下のテンプレートを使う。

#### 3-A. CI 成功時

```
## 次のアクション

1. /aidea.merge — PR をマージしてローカル main を更新する
2. PR にレビュー依頼のコメントを書く
3. 別ブランチの作業に移る
4. 何もしない (このまま待機)

番号で選んでね。
```

#### 3-B. 諦め (修正不能) 時

```
## 次のアクション

1. 失敗ログを詳しく見る (`gh run view <run-id> --log-failed`)
2. 手動で修正してコミット & push する
3. /aidea.ci-watch を再実行する (修正後にもう一度任せる)
4. 委譲先 Companion を変えて再実行 (例: `/aidea.ci-watch <companion-name>`)
5. 中止して別の作業に移る

番号で選んでね。
```

#### 3-C. 上限到達時

```
## 次のアクション

1. 失敗ログを詳しく見る (`gh run view <run-id> --log-failed`)
2. 試行履歴をもとに自分で原因分析・修正する
3. /aidea.ci-watch を再実行する (キャッシュや一時的な失敗の可能性)
4. 委譲先 Companion を変えて再実行する
5. PR を一旦クローズして仕切り直す
6. 中止して別の作業に移る

番号で選んでね。
```

提案する候補の数は 3〜6 個を目安に、状況に合わせて適宜増減して構わない (機械的に固定しない)。各候補は **動詞で始まる短い 1 行** で、ユーザがすぐ判断できる粒度にする。

## 委譲モード (引数あり) のやること

### 1. ハンドオフ送信

`.aidea/claude/handoff.md` の手順に従って、指定された Companion に以下の内容をハンドオフする。

- `task`: `ci-fix`
- `message`: 以下のテンプレート

```
/aidea.ci-fix を実行して、結果を私 (Companion <自分のN>) にハンドオフバックで返してね。

報告フォーマット (どれか 1 つを selected フィールドに含めて返して):
- success: CI 通過
- pushed: 修正して push した
- in_progress: 進行中 (修正なし)
- abandoned: 修正不能で停止 (理由を併記)

試行回数: <現在の試行回数>/3
```

ハンドオフ送信後、自分のターンは終了する (ハンドオフバック待ち)。

### 2. ハンドオフバック受信時

委譲先の Companion からハンドオフバックを受けたら、`message` 内の `selected` を読み取って判定:

- **success**: ローカルモードの「2-A」と同じ報告 + 「3-A」次のアクション提案で終了
- **pushed**: 試行回数が 3 未満なら 10 分待ってから再度ハンドオフ。3 回目なら「2-C」上限到達報告 + 「3-C」次のアクション提案で終了
- **in_progress**: pushed と同じ扱い (10 分待って再ハンドオフ)
- **abandoned**: ローカルモードの「2-B」諦め報告 + 「3-B」次のアクション提案で終了

委譲モードでも、ローカルモードの「3. 次のアクション提案」を必ず提示すること。

### 3. 試行回数の管理

委譲モードでは、ハンドオフ message に `試行回数: N/3` を含めて、ハンドオフバックでもその値を引き継いでもらう。受信時に N+1 して次のハンドオフに渡す。

## 注意

- このスキルは **同期的に sleep でブロックして待機する** (10 分単位)。長時間ジョブとなる点に留意
- 委譲モードではハンドオフバックを受けるまで自分は無応答になる。Companion 側がハンドオフバックを忘れると 1 回で終わってしまうため、message に明示する
- `aidea.ci-fix` 自体はリトライしない設計なので、リトライ責務はこのスキルが持つ
- 修正不能と判断された時点で打ち切る (3 回まで粘らない)
- 進行中で修正なし、が 3 回連続した場合は「上限到達」報告に含めて、CI が動いていない可能性も指摘する
