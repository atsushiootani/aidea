# aidea.ci-fix

GitHub Actions の CI ステータスを **1 度だけ** 確認し、失敗があれば自動修正して push、成功 / 進行中ならその旨を報告して終了するスキル。リトライ・待機ループは持たない (リトライしたい場合は呼び出し側でこのスキルを再度呼ぶ)。

## 使い方

- **手動起動**: 現在のブランチの PR の CI 結果を 1 度確認したいときに実行する
- **自動起動**: `<github-webhook-activity>` で CI 失敗イベントを受信したとき自動で呼び出す
- **連携**: `aidea.ci-watch` から失敗時の修正処理として呼び出される

## やること

### 1. 対象 PR の特定

`git rev-parse --abbrev-ref HEAD` でブランチ名を取得し、対応する PR を `mcp__github__list_pull_requests` で特定する。

- PR が見つからない場合はユーザに確認して停止する
- PR の state が `open` でない場合も停止する

### 2. CI ステータスの確認

`mcp__github__pull_request_read` で PR の check runs を取得し、各ジョブの状態を分類する。

- **すべて成功** (`SUCCESS` / `NEUTRAL` / `SKIPPED`): 「CI は通過しています」と報告して終了する
- **進行中あり** (`IN_PROGRESS` / `QUEUED` / `PENDING`、失敗ゼロ): 進行中チェック一覧をユーザに報告して終了する (待機しない)
- **失敗あり** (`FAILURE` / `CANCELLED` / `TIMED_OUT` / `ACTION_REQUIRED` / `STARTUP_FAILURE`): 次のステップへ進む

### 3. ビルドログの取得と解析

`mcp__github__get_commit` などを使ってログを取得し、以下を解析する:

- コンパイルエラー (型不一致 / 未定義シンボル / アクセス制御 等)
- テスト失敗 (assertion failure / crash 等)
- エラーが含まれるファイルパスと行番号を特定する

### 4. 修正の実施

エラーが含まれる Swift ファイルを Read → Edit で修正する。

修正指針:
- コンパイルエラーはエラーメッセージを根拠に最小変更で修正する
- テスト失敗は実装バグか仕様バグかを判断し、実装を修正する (仕様変更は手動確認が必要なためスキップ)
- 1 回の修正で複数ファイルを変更して構わない

修正対象が判別できない / 仕様変更が必要と判断した場合は、修正を行わずに状況をユーザに報告して終了する。

### 5. コミット & プッシュ

```
git add <変更ファイル>
git commit -m "fix: CI エラーを修正"
git push origin <branch>
```

### 6. 終了報告

push 完了後、以下のフォーマットでユーザに報告して終了する。**再確認や再修正のための待機・リトライは行わない** (再確認したい場合はユーザが `/aidea.ci-fix` または `/aidea.ci-watch` を再度呼ぶ)。

```
🔧 CI エラーを修正して push しました。

## 修正内容
<修正したファイルと変更概要>

## コミット
<コミット SHA> — fix: CI エラーを修正

## 次のアクション
GitHub Actions の再実行が完了したら /aidea.ci-watch でステータスを再確認してください。
```

## 注意

- このスキルは **必ず 1 度きりで終了** する。push 後の再確認・追加修正は行わない
- UI テスト (`AideaUITests`) の失敗は CI ワークフロー側で除外しているため対象外
- 仕様変更が必要な修正 (API 変更・設計変更) は自動修正せずユーザに委ねる
- `git push --force` は使わない
- 修正内容は最小限にとどめ、無関係なリファクタリングは行わない
