# aidea.ci-fix

GitHub Actions の CI 失敗を検知し、Swift ビルドエラー・テストエラーを自動修正するスキル。

## 使い方

- **手動起動**: 現在のブランチの PR が CI 失敗しているときに実行する
- **自動起動**: `<github-webhook-activity>` で CI 失敗イベントを受信したとき自動で呼び出す

## やること

### 1. 対象 PR の特定

`git rev-parse --abbrev-ref HEAD` でブランチ名を取得し、対応する PR を `mcp__github__list_pull_requests` で特定する。

- PR が見つからない場合はユーザに確認して停止する
- PR の state が `open` でない場合も停止する

### 2. CI ステータスの確認

`mcp__github__pull_request_read` で PR の check runs を取得し、失敗しているジョブを特定する。

- **全ジョブが成功 / pending**: 「CI は通過しています」と報告して終了する
- **失敗ジョブあり**: 次のステップへ進む

### 3. ビルドログの取得と解析

`mcp__github__get_commit` などを使ってログを取得し、以下を解析する:

- コンパイルエラー (型不一致 / 未定義シンボル / アクセス制御 等)
- テスト失敗 (assertion failure / crash 等)
- エラーが含まれるファイルパスと行番号を特定する

### 4. 修正の実施

エラーが含まれる Swift ファイルを Read → Edit で修正する。

修正指針:
- コンパイルエラーはエラーメッセージを根拠に最小変更で修正する
- テスト失敗は実装バグか仕様バグかを判断し、実装を修正する (仕様変更は手動確認が必要なためスキップ)
- 1 回の修正で複数ファイルを変更して構わない

### 5. コミット & プッシュ

```
git add <変更ファイル>
git commit -m "fix: CI エラーを修正 (試行 N/3)"
git push origin <branch>
```

コミットメッセージに試行回数を含める。

### 6. リトライ制御

修正 push 後、GitHub Actions が再実行されるまで **90 秒待機** し、再度ステップ 2 に戻る。

| 試行回数 | 結果 | 次のアクション |
|---|---|---|
| 1〜3 回 | 失敗継続 | 再修正して push |
| 1〜3 回 | 成功 | 「CI が通過しました」と報告して終了 |
| 3 回完了後も失敗 | — | 下記「修正不能時の報告」へ |

### 7. 修正不能時の報告

3 回試みても CI が通過しない場合、**ルーティンを停止**して以下をユーザに報告する:

```
⚠️ CI が 3 回の自動修正後も通過しませんでした。

## 最後のエラー
<ビルドエラー / テスト失敗の詳細>

## 試みた修正
1. <コミット SHA> — <修正内容の概要>
2. <コミット SHA> — <修正内容の概要>
3. <コミット SHA> — <修正内容の概要>

## 推奨アクション
<根本原因の推定と次に確認すべき箇所>
```

## 注意

- UI テスト (`AideaUITests`) の失敗は CI ワークフロー側で除外しているため対象外
- 仕様変更が必要な修正 (API 変更・設計変更) は自動修正せずユーザに委ねる
- `git push --force` は使わない
- 修正内容は最小限にとどめ、無関係なリファクタリングは行わない
