# Gitワークフローとバージョニング

## 概要

Gitはあなたの安全網。コミットはセーブポイント、ブランチはサンドボックス、履歴はドキュメンテーションとして扱う。AIエージェントが高速にコードを生成する時代、規律あるバージョン管理は変更を管理可能・レビュー可能・可逆に保つ仕組み。

## 使うとき

常に。すべてのコード変更はgitを通る。

## 核となる原則

### トランクベース開発（推奨）

`main` を常にデプロイ可能に保つ。1〜3日以内にマージされる短命の機能ブランチで作業する。長命の開発ブランチは隠れたコスト――分岐してマージ衝突を生み統合を遅らせる。DORAの研究は一貫してトランクベース開発が高パフォーマンスチームと相関することを示す。

```
main ──●──●──●──●──●──●──●──●──●──  (常にデプロイ可能)
        ╲      ╱  ╲    ╱
         ●──●─╱    ●──╱    ← 短命機能ブランチ（1〜3日）
```

これが推奨デフォルト。gitflowや長命ブランチを使うチームも原則（アトミックコミット、小変更、説明的メッセージ）を自分のブランチモデルに適応できる――特定のブランチ戦略よりコミット規律が重要。

- **Devブランチはコスト。** ブランチが生きる日ごとにマージリスクが蓄積する。
- **リリースブランチは許容。** main を進めつつリリースを安定化する必要があるとき。
- **フィーチャーフラグ > 長命ブランチ。** 未完成作業を数週間ブランチに置くよりフラグ裏でデプロイする方を選ぶ。

### 1. 早くコミット、頻繁にコミット

各成功インクリメントが独自のコミットを得る。大きな未コミット変更を溜めない。

```
作業パターン:
  スライス実装 → テスト → 検証 → コミット → 次スライス

こうではない:
  全部実装 → 動くことを祈る → 巨大コミット
```

コミットはセーブポイント。次の変更が何かを壊したら、直前の既知の良い状態に即座に戻れる。

### 2. アトミックコミット

各コミットは1つの論理的なことを行う:

```
# 良: 各コミットが自己完結
git log --oneline
a1b2c3d 検証付きのタスク作成エンドポイントを追加
d4e5f6g タスク作成フォームコンポーネントを追加
h7i8j9k フォームを API に接続しローディング状態を追加
m1n2o3p タスク作成のテストを追加（ユニット + 統合）

# 悪: 全部混在
git log --oneline
x1y2z3a タスク機能を追加、サイドバー修正、依存更新、ユーティリティをリファクタ
```

### 3. 説明的メッセージ

コミットメッセージは *何* ではなく *なぜ* を説明:

```
# 良: 意図を説明
feat: 登録エンドポイントにメール検証を追加

無効なメール形式がデータベースに到達するのを防ぐ。
auth.ts の既存の検証パターンと一貫性を持たせるため、
ルートハンドラレベルで Zod スキーマ検証を使う。

# 悪: 差分から明らかなことを書く
update auth.ts
```

**形式:**
```
<type>: <短い説明>

<任意の本文。何ではなくなぜを説明する>
```

**タイプ:**
- `feat` ――新機能
- `fix` ――バグ修正
- `refactor` ――バグ修正でも機能追加でもないコード変更
- `test` ――テストの追加・更新
- `docs` ――ドキュメントのみ
- `chore` ――ツール、依存、設定

### 4. 関心事を分ける

フォーマット変更を挙動変更と混ぜない。リファクタと機能を混ぜない。各タイプの変更は別コミット――理想的には別PR:

```
# 良: 関心事を分離
git commit -m "refactor: 検証ロジックを共有ユーティリティに抽出"
git commit -m "feat: 登録に電話番号検証を追加"

# 悪: 関心事混在
git commit -m "検証をリファクタして電話番号フィールドを追加"
```

**リファクタと機能作業を分離する。** リファクタリング変更と機能変更は2つの異なる変更――別々にサブミットする。これで各変更がレビュー、リバート、履歴理解が容易になる。小さなクリーンアップ（変数リネーム）はレビュアーの裁量で機能コミットに含めてよい。

### 5. 変更サイズ

コミット/PRあたり~100行を目指す。~1000行超は分割する。大きな変更の分解方法は `code-review-and-quality` の分割戦略を参照。

```
~100行   → レビューしやすく、リバートしやすい
~300行   → 単一論理変更なら許容
~1000行  → 小さな変更に分割
```

## ブランチ戦略

### フィーチャーブランチ

```
main (常にデプロイ可能)
  │
  ├── feature/task-creation    ← ブランチあたり1機能
  ├── feature/user-settings    ← 並行作業
  └── fix/duplicate-tasks      ← バグ修正
```

- `main` （またはチームのデフォルトブランチ）から分岐
- ブランチを短命に保つ（1〜3日以内にマージ） ――長命ブランチは隠れコスト
- マージ後ブランチ削除
- 未完成機能には長命ブランチよりフィーチャーフラグを優先

### ブランチ命名

```
feature/<short-description>   → feature/task-creation
fix/<short-description>       → fix/duplicate-tasks
chore/<short-description>     → chore/update-deps
refactor/<short-description>  → refactor/auth-module
```

## ワークツリーの利用

並行AIエージェント作業には、複数ブランチを同時実行するためgit worktreeを使う:

```bash
# 機能ブランチ用worktree作成
git worktree add ../project-feature-a feature/task-creation
git worktree add ../project-feature-b feature/user-settings

# 各worktreeは独自ブランチを持つ別ディレクトリ
# エージェントが干渉せず並行作業可能
ls ../
  project/              ← mainブランチ
  project-feature-a/    ← task-creationブランチ
  project-feature-b/    ← user-settingsブランチ

# 完了したらマージしてクリーンアップ
git worktree remove ../project-feature-a
```

利点:
- 複数エージェントが異なる機能で同時作業可能
- ブランチ切替不要（各ディレクトリが独自ブランチを持つ）
- 実験失敗時はworktree削除――何も失わない
- 明示的マージまで変更は隔離

## セーブポイントパターン

```
エージェント作業開始
    │
    ├── 変更を加える
    │   ├── テスト通過? → コミット → 続行
    │   └── テスト失敗? → 直前コミットに戻す → 調査
    │
    ├── 別の変更
    │   ├── テスト通過? → コミット → 続行
    │   └── テスト失敗? → 直前コミットに戻す → 調査
    │
    └── 機能完了 → 全コミットがクリーンな履歴を形成
```

このパターンで1インクリメント以上の作業を失わない。エージェントが脱線しても `git reset --hard HEAD` で直前の成功状態に戻る。

## 変更サマリー

修正後は構造化サマリーを提供する。レビューを容易にし、スコープ規律を記録し、意図しない変更を浮き彫りにする:

```
行った変更:
- src/routes/tasks.ts: POSTエンドポイントに検証ミドルウェア追加
- src/lib/validation.ts: ZodでTaskCreateSchema追加

触らなかったもの（意図的）:
- src/routes/auth.ts: 似た検証の欠如があるが範囲外
- src/middleware/error.ts: エラー形式を改善できる（別タスク）

潜在的懸念:
- Zodスキーマが厳格――追加フィールドを拒否。意図通りか確認を。
- zodを依存に追加（72KB gzipped）――package.jsonに既にある
```

このパターンは誤った仮定を早期に捕え、レビュアーに変更の明確な地図を与える。「触らなかった」セクションが特に重要――スコープ規律を発揮し、依頼のない改装に走っていないことを示す。

## コミット前衛生

各コミット前に:

```bash
# 1. コミットしようとするものを確認
git diff --staged

# 2. シークレットがないことを確認
git diff --staged | grep -i "password\|secret\|api_key\|token"

# 3. テスト実行
npm test

# 4. lint実行
npm run lint

# 5. 型チェック実行
npx tsc --noEmit
```

gitフックで自動化:

```json
// package.json（lint-staged + husky使用）
{
  "lint-staged": {
    "*.{ts,tsx}": ["eslint --fix", "prettier --write"],
    "*.{json,md}": ["prettier --write"]
  }
}
```

## 生成ファイルの扱い

- プロジェクトが期待する場合のみ**生成ファイルをコミット**（例: `package-lock.json`、Prismaマイグレーション）
- ビルド出力（`dist/`、`.next/`）、環境ファイル（`.env`）、IDE設定（`.vscode/settings.json` は共有しない限り）は**コミットしない**
- `.gitignore` に以下を含める: `node_modules/`、`dist/`、`.env`、`.env.local`、`*.pem`

## デバッグへのgit活用

```bash
# バグを入れたコミットを見つける
git bisect start
git bisect bad HEAD
git bisect good <known-good-commit>
# Gitが中間をチェックアウト、各時点でテスト実行して絞り込む

# 最近の変更を見る
git log --oneline -20
git diff HEAD~5..HEAD -- src/

# 特定行を誰が最後に変えたか
git blame src/services/task.ts

# コミットメッセージのキーワード検索
git log --grep="validation" --oneline
```

## よくある言い訳

| 言い訳 | 現実 |
|---|---|
| 「機能が完成したらコミットする」 | 1つの巨大コミットはレビュー・デバッグ・リバート不能。各スライスをコミット。 |
| 「メッセージは重要じゃない」 | メッセージはドキュメント。将来の自分（そしてエージェント）が何が変わりなぜかを理解する必要がある。 |
| 「後でsquashする」 | squashは開発の物語を破壊する。最初からクリーンな段階コミットを。 |
| 「ブランチはオーバーヘッド」 | 短命ブランチは無料で衝突作業を防ぐ。問題は長命ブランチ――1〜3日以内にマージ。 |
| 「この変更は後で分割する」 | 大きな変更はレビューしにくく、デプロイ危険で、リバートが難しい。サブミット前に分ける。 |
| 「`.gitignore` は不要」 | 本番シークレット入りの `.env` がコミットされるまでは。即セットアップ。 |

## レッドフラグ

- 大きな未コミット変更が溜まる
- 「fix」「update」「misc」のようなコミットメッセージ
- フォーマット変更と挙動変更が混在
- プロジェクトに `.gitignore` がない
- `node_modules/`、`.env`、ビルド成果物をコミット
- main から大きく分岐した長命ブランチ
- 共有ブランチへのforce push

## 検証

すべてのコミットで:

- [ ] コミットが1つの論理的なこと
- [ ] メッセージがなぜかを説明、タイプ規約に従う
- [ ] コミット前にテスト通過
- [ ] 差分にシークレットなし
- [ ] フォーマットのみの変更が挙動変更と混在していない
- [ ] `.gitignore` が標準的除外をカバー
