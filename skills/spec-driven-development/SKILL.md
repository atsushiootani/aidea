# スペック駆動開発

## 概要

コードを書く前に構造化された仕様を書く。スペックはあなたと人間エンジニアの間の真実の源 — 何を作るのか、なぜ作るのか、そしてどうやって完了を判断するかを定義する。スペックなしのコードは推測でしかない。

## 使うタイミング

- 新規プロジェクトや機能を始めるとき
- 要件が曖昧または不完全なとき
- 変更が複数のファイルやモジュールに及ぶとき
- アーキテクチャ決定を下そうとしているとき
- 実装に30分以上かかるタスク

**使わないとき:** 1行修正、タイポ修正、要件が明確で自己完結している変更。

## ゲート化されたワークフロー

スペック駆動開発には4つのフェーズがある。現在のフェーズが検証されるまで次のフェーズに進まない。

```
SPECIFY ──→ PLAN ──→ TASKS ──→ IMPLEMENT
   │          │        │          │
   ▼          ▼        ▼          ▼
 人間が     人間が   人間が     人間が
 レビュー   レビュー レビュー   レビュー
```

### フェーズ1: Specify

高レベルのビジョンから始める。要件が具体的になるまで人間に明確化質問をする。

**前提をすぐに表面化する。** スペックの内容を書く前に、前提していることを列挙する:

```
私が置いている前提:
1. これは Web アプリケーションである（ネイティブモバイルではない）
2. 認証はセッションベースの cookie を使う（JWT ではない）
3. データベースは PostgreSQL である（既存の Prisma スキーマに基づく）
4. モダンブラウザのみを対象とする（IE11 非対応）
→ 今のうちに訂正して、なければこのまま進めます。
```

曖昧な要件をサイレントに埋めないこと。スペックの目的全体は、コードが書かれる*前に*誤解を表面化すること — 前提は最も危険な形の誤解。

**以下の6つのコアエリアをカバーするスペック文書を書く:**

1. **Objective（目的）** — 何を、なぜ作るのか？ユーザーは誰か？成功はどう見えるか？

2. **Commands（コマンド）** — ツール名だけでなく、フラグ付きの完全な実行可能コマンド。
   ```
   ビルド: npm run build
   テスト: npm test -- --coverage
   リント: npm run lint --fix
   開発: npm run dev
   ```

3. **Project Structure（プロジェクト構造）** — ソースコードの場所、テストの場所、ドキュメントの場所。
   ```
   src/           → アプリケーションのソースコード
   src/components → React コンポーネント
   src/lib        → 共有ユーティリティ
   tests/         → ユニットおよび統合テスト
   e2e/           → エンドツーエンドテスト
   docs/          → ドキュメント
   ```

4. **Code Style（コードスタイル）** — 実際のコードスニペット1つが3段落の説明に勝る。命名規則、フォーマットルール、良い出力例を含める。

5. **Testing Strategy（テスト戦略）** — どのフレームワーク、テストの置き場所、カバレッジ期待値、どの関心事にどのテストレベルか。

6. **Boundaries（境界）** — 3層システム:
   - **Always do:** コミット前のテスト実行、命名規則の遵守、入力の検証
   - **Ask first:** データベーススキーマ変更、依存関係追加、CI設定変更
   - **Never do:** シークレットのコミット、ベンダーディレクトリ編集、承認なしの失敗テスト削除

**スペックテンプレート:**

```markdown
# スペック: [プロジェクト/機能名]

## 目的
[何を、なぜ作るか。ユーザーストーリーまたは受入基準。]

## 技術スタック
[フレームワーク、言語、主要依存とバージョン]

## コマンド
[ビルド、テスト、リント、開発 — 完全なコマンド]

## プロジェクト構造
[ディレクトリレイアウトと説明]

## コードスタイル
[例となるスニペット + 主要な規約]

## テスト戦略
[フレームワーク、テストの場所、カバレッジ要件、テストレベル]

## 境界
- Always（常にやる）: [...]
- Ask first（先に確認）: [...]
- Never（決してやらない）: [...]

## 成功基準
[完了をどう判断するか — 具体的でテスト可能な条件]

## オープンな疑問
[未解決で人間の入力が必要なもの]
```

**指示を成功基準として再構成する。** 曖昧な要件を受け取ったら、具体的な条件に翻訳する:

```
要件: 「ダッシュボードを速くして」

再構成した成功基準:
- 4G 接続でダッシュボードの LCP が 2.5 秒未満
- 初期データロードが 500ms 未満で完了
- ロード中のレイアウトシフトなし（CLS < 0.1）
→ このターゲットで合っていますか?
```

これによって「速い」が何を意味するか推測する代わりに、明確なゴールに向かってループし、リトライし、問題解決できる。

### フェーズ2: Plan

検証されたスペックを元に、技術的実装計画を生成:

1. 主要コンポーネントとその依存関係を特定
2. 実装順序を決定（何が先に作られなければならないか）
3. リスクと緩和戦略を記録
4. 並行して作れるものと順次に作らないといけないものを特定
5. フェーズ間の検証チェックポイントを定義

計画はレビュー可能であるべき: 人間が読んで「はい、正しいアプローチ」または「いいえ、Xを変えて」と言えるべき。

### フェーズ3: Tasks

計画を個別の実装可能タスクに分解:

- 各タスクは1つの集中セッションで完了できるべき
- 各タスクには明示的な受入基準がある
- 各タスクには検証ステップ（テスト、ビルド、手動チェック）が含まれる
- タスクは認識された重要度ではなく依存関係で順序付け
- どのタスクもおよそ5ファイル以上を変更するべきではない

**タスクテンプレート:**
```markdown
- [ ] タスク: [説明]
  - 受入条件: [完了時に真でなければならないこと]
  - 検証方法: [どう確認するか — テストコマンド、ビルド、手動チェック]
  - ファイル: [どのファイルを変更するか]
```

### フェーズ4: Implement

`incremental-implementation` と `test-driven-development` スキルに従ってタスクを1つずつ実行。`context-engineering` を使って各ステップで適切なスペックセクションとソースファイルをロードし、エージェントにスペック全体を流し込まない。

## スペックを生きたものに保つ

スペックは一度限りの成果物ではなく、生きた文書:

- **決定が変わったら更新する** — データモデルを変える必要があると判明したら、まずスペックを更新してから実装する。
- **スコープが変わったら更新する** — 追加・削除された機能はスペックに反映する。
- **スペックをコミットする** — スペックはコードとともにバージョン管理に属する。
- **PRでスペックを参照する** — 各PRが実装するスペックセクションにリンクバック。

## よくある言い訳

| 言い訳 | 現実 |
|---|---|
| "これはシンプルだからスペックは要らない" | シンプルなタスクは*長い*スペックは不要だが、それでも受入基準は要る。2行のスペックで十分。 |
| "コードを書いた後にスペックを書く" | それはドキュメントであってスペックではない。スペックの価値はコード*前に*明確性を強いること。 |
| "スペックは遅くする" | 15分のスペックが数時間の手戻りを防ぐ。15分のウォーターフォールは15時間のデバッグに勝る。 |
| "要件はどうせ変わる" | だからこそスペックは生きた文書。古いスペックでもスペックなしよりマシ。 |
| "ユーザーは何が欲しいかわかっている" | 明確なリクエストにも暗黙の前提がある。スペックはそれを表面化する。 |

## レッドフラグ

- 書面の要件なしにコードを書き始める
- 「もう作り始めていいですか？」と「完了」が何を意味するか明確化する前に聞く
- どのスペックやタスクリストにも言及されていない機能を実装する
- ドキュメント化せずにアーキテクチャ決定を下す
- 「何を作るか明らか」という理由でスペックをスキップする

## 検証

実装に進む前に確認:

- [ ] スペックが6つのコアエリアすべてをカバーしている
- [ ] 人間がスペックをレビュー・承認した
- [ ] 成功基準が具体的でテスト可能
- [ ] 境界（Always/Ask First/Never）が定義されている
- [ ] スペックがリポジトリ内のファイルに保存されている
