# 出荷とローンチ

## 概要

自信を持って出荷する。目標は単にデプロイすることではない――安全にデプロイし、監視を整え、ロールバック計画を準備し、成功の姿を明確に理解してデプロイすること。すべてのローンチは可逆、観測可能、段階的であるべき。

## 使うとき

- 機能を初めて本番にデプロイするとき
- 重要な変更をユーザーにリリース
- データやインフラをマイグレート
- ベータや早期アクセスプログラムを開始
- リスクを伴うデプロイ（全デプロイ）

## ローンチ前チェックリスト

### コード品質

- [ ] すべてのテスト通過（ユニット、統合、e2e）
- [ ] ビルドが警告なしで成功
- [ ] lintと型チェック通過
- [ ] コードレビュー・承認済み
- [ ] ローンチ前に解決すべきTODOコメントなし
- [ ] 本番コードにデバッグ用 `console.log` なし
- [ ] 予期される失敗モードをエラーハンドリングがカバー

### セキュリティ

- [ ] コードやバージョン管理にシークレットなし
- [ ] `npm audit` が critical/high 脆弱性ゼロ
- [ ] 全ユーザー向けエンドポイントで入力検証
- [ ] 認証・認可チェック配置
- [ ] セキュリティヘッダー設定（CSP、HSTS等）
- [ ] 認証エンドポイントにレートリミット
- [ ] CORSが特定origin（ワイルドカードではない）

### パフォーマンス

- [ ] Core Web Vitals が「良好」しきい値内
- [ ] クリティカルパスにN+1クエリなし
- [ ] 画像最適化済み（圧縮、レスポンシブサイズ、遅延ロード）
- [ ] バンドルサイズが予算内
- [ ] DBクエリに適切なインデックス
- [ ] 静的アセットと繰返しクエリ用にキャッシュ設定

### アクセシビリティ

- [ ] すべてのインタラクティブ要素でキーボードナビゲーションが動く
- [ ] スクリーンリーダーがページ内容と構造を伝えられる
- [ ] カラーコントラストがWCAG 2.1 AA を満たす（テキスト4.5:1）
- [ ] モーダルや動的コンテンツのフォーカス管理が正しい
- [ ] エラーメッセージが説明的でフォームフィールドに紐付け
- [ ] axe-coreやLighthouseにアクセシビリティ警告なし

### インフラ

- [ ] 本番で環境変数設定済み
- [ ] DBマイグレーション適用済み（または適用準備完了）
- [ ] DNSとSSL設定済み
- [ ] 静的アセット用CDN設定
- [ ] ロギングとエラー報告設定
- [ ] ヘルスチェックエンドポイント存在・応答

### ドキュメント

- [ ] READMEが新しいセットアップ要件で更新済み
- [ ] APIドキュメント最新
- [ ] アーキテクチャ決定のADR記述済み
- [ ] Changelog更新
- [ ] ユーザー向けドキュメント更新（該当時）

## フィーチャーフラグ戦略

フラグ裏で出荷してデプロイとリリースを分離:

```typescript
// フィーチャーフラグチェック
const flags = await getFeatureFlags(userId);

if (flags.taskSharing) {
  // 新機能: タスク共有
  return <TaskSharingPanel task={task} />;
}

// デフォルト: 既存挙動
return null;
```

**フィーチャーフラグライフサイクル:**

```
1. フラグOFFでデプロイ          → コードは本番にあるが非アクティブ
2. チーム/ベータで有効化         → 本番環境で内部テスト
3. 段階的ロールアウト            → ユーザーの5% → 25% → 50% → 100%
4. 各段階で監視                 → エラー率、パフォーマンス、ユーザーフィードバック
5. クリーンアップ               → 完全ロールアウト後フラグとデッドコードパスを削除
```

**ルール:**
- すべてのフィーチャーフラグに所有者と期限がある
- 完全ロールアウト後2週間以内にフラグをクリーンアップ
- フラグをネストしない（指数的組み合わせを生む）
- CIで両方の状態（ONとOFF）をテスト

## 段階的ロールアウト

### ロールアウト順序

```
1. ステージングにデプロイ
   └── ステージング環境で全テストスイート
   └── 重要フローの手動スモークテスト

2. 本番にデプロイ（フィーチャーフラグOFF）
   └── デプロイ成功を検証（ヘルスチェック）
   └── エラー監視チェック（新エラーなし）

3. チーム向けに有効化（内部ユーザー用フラグON）
   └── チームが本番で機能を使う
   └── 24時間監視ウィンドウ

4. カナリアロールアウト（ユーザー5%にフラグON）
   └── エラー率、レイテンシ、ユーザー挙動を監視
   └── メトリクス比較: カナリア vs ベースライン
   └── 24〜48時間監視ウィンドウ
   └── 全しきい値が通る場合のみ進む（下の表参照）

5. 段階的増加（25% -> 50% -> 100%）
   └── 各ステップで同じ監視
   └── 任意時点で前のパーセンテージにロールバック可能

6. 全ロールアウト（全ユーザーにフラグON）
   └── 1週間監視
   └── フィーチャーフラグをクリーンアップ
```

### ロールアウト判断しきい値

各段階で進む、保留、ロールバックを決めるしきい値:

| 指標 | 進む（緑） | 保留し調査（黄） | ロールバック（赤） |
|--------|-----------------|-------------------------------|-----------------|
| エラー率 | ベースラインの10%以内 | ベースライン10〜100%上 | ベースラインの2倍超 |
| P95レイテンシ | ベースラインの20%以内 | ベースライン20〜50%上 | ベースラインの50%超 |
| クライアントJSエラー | 新エラータイプなし | セッションの0.1%未満で新エラー | セッションの0.1%超で新エラー |
| ビジネス指標 | 中立またはプラス | 5%未満低下（ノイズの可能性） | 5%超低下 |

### いつロールバックするか

即時ロールバック:
- エラー率がベースラインの2倍超に増加
- P95レイテンシが50%超増加
- ユーザー報告問題が急増
- データ整合性問題検出
- セキュリティ脆弱性発見

## 監視と観測性

### 何を監視するか

```
アプリケーション指標:
├── エラー率（総計とエンドポイント別）
├── 応答時間（p50、p95、p99）
├── リクエスト量
├── アクティブユーザー
└── 主要ビジネス指標（コンバージョン、エンゲージメント）

インフラ指標:
├── CPU・メモリ使用率
├── DB接続プール使用率
├── ディスク容量
├── ネットワークレイテンシ
└── キュー深さ（該当時）

クライアント指標:
├── Core Web Vitals（LCP、INP、CLS）
├── JavaScriptエラー
├── クライアント視点からのAPIエラー率
└── ページロード時間
```

### エラー報告

```typescript
// 報告付きエラーバウンダリ
class ErrorBoundary extends React.Component {
  componentDidCatch(error: Error, info: React.ErrorInfo) {
    // エラー追跡サービスに報告
    reportError(error, {
      componentStack: info.componentStack,
      userId: getCurrentUser()?.id,
      page: window.location.pathname,
    });
  }

  render() {
    if (this.state.hasError) {
      return <ErrorFallback onRetry={() => this.setState({ hasError: false })} />;
    }
    return this.props.children;
  }
}

// サーバー側エラー報告
app.use((err: Error, req: Request, res: Response, next: NextFunction) => {
  reportError(err, {
    method: req.method,
    url: req.url,
    userId: req.user?.id,
  });

  // ユーザーに内部を露出しない
  res.status(500).json({
    error: { code: 'INTERNAL_ERROR', message: 'Something went wrong' },
  });
});
```

### ローンチ後検証

ローンチ後最初の1時間に:

```
1. ヘルスエンドポイントが200を返すか確認
2. エラー監視ダッシュボードを確認（新エラータイプなし）
3. レイテンシダッシュボードを確認（リグレッションなし）
4. 重要ユーザーフローを手動テスト
5. ログが流れて読めるか確認
6. ロールバック機構が動くか確認（可能ならドライラン）
```

## ロールバック戦略

すべてのデプロイは起こる前にロールバック計画が必要:

```markdown
## [機能/リリース]のロールバック計画

### トリガー条件
- エラー率 > ベースラインの2倍
- P95レイテンシ > [X]ms
- [特定問題]のユーザー報告

### ロールバック手順
1. フィーチャーフラグを無効化（該当時）
   または
1. 前バージョンをデプロイ: `git revert <commit> && git push`
2. ロールバック検証: ヘルスチェック、エラー監視
3. 通信: チームにロールバックを通知

### データベース考慮事項
- マイグレーション[X]にロールバックあり: `npx prisma migrate rollback`
- 新機能が挿入したデータ: [保存 / 削除]

### ロールバック時間
- フィーチャーフラグ: < 1分
- 前バージョン再デプロイ: < 5分
- DBロールバック: < 15分
```

## よくある言い訳

| 言い訳 | 現実 |
|---|---|
| 「ステージングで動いたから本番でも動く」 | 本番は異なるデータ、トラフィックパターン、エッジケースを持つ。デプロイ後監視を。 |
| 「これにフィーチャーフラグは不要」 | どの機能もキルスイッチの恩恵を受ける。「シンプル」な変更でも壊れうる。 |
| 「監視はオーバーヘッド」 | 監視がないとダッシュボードでなくユーザー苦情から問題を発見する羽目に。 |
| 「監視は後で追加」 | ローンチ前に追加。見えないものはデバッグできない。 |
| 「ロールバックは失敗を認めること」 | ロールバックは責任あるエンジニアリング。壊れた機能を出荷する方が失敗。 |

## レッドフラグ

- ロールバック計画なしのデプロイ
- 本番に監視・エラー報告なし
- ビッグバンリリース（全部を一度に、ステージングなし）
- 期限や所有者のないフィーチャーフラグ
- ローンチ初の1時間を誰も監視しない
- 本番環境設定が記憶で行われる（コードでなく）
- 「金曜午後だ、出荷しよう」

## 検証

デプロイ前:

- [ ] ローンチ前チェックリスト完了（全セクション緑）
- [ ] フィーチャーフラグ設定（該当時）
- [ ] ロールバック計画ドキュメント化
- [ ] 監視ダッシュボード設定
- [ ] チームにデプロイ通知

デプロイ後:

- [ ] ヘルスチェックが200を返す
- [ ] エラー率が正常
- [ ] レイテンシが正常
- [ ] 重要ユーザーフローが動く
- [ ] ログが流れている
- [ ] ロールバックがテスト済みまたは準備完了
