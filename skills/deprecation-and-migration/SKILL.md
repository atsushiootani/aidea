# 廃止予定とマイグレーション

## 概要

コードは資産ではなく負債。すべての行は継続的なメンテコストを持つ――直すバグ、更新する依存、適用するセキュリティパッチ、オンボードする新エンジニア。廃止予定はもはや価値を持たないコードを取り除く規律であり、マイグレーションはユーザーを安全に古いものから新しいものへ移すプロセス。

ほとんどのエンジニアリング組織は構築は得意。取り除くのが得意なところは少ない。このスキルはその隙間に対処する。

## 使うとき

- 古いシステム、API、ライブラリを新しいものに置き換える
- 不要になった機能をサンセット
- 重複実装を統合
- 誰も所有していないが皆が依存するデッドコードを削除
- 新システムのライフサイクル計画（廃止予定計画は設計時に始まる）
- レガシー維持かマイグレーション投資かを決める

## 核となる原則

### コードは負債

すべての行は継続的コストを持つ: テスト、ドキュメント、セキュリティパッチ、依存更新、周辺作業者のメンタルオーバーヘッドが必要。コードの価値は提供する機能であってコード自体ではない。同じ機能がより少ないコード、少ない複雑さ、より良い抽象で提供できるなら――古いコードは去るべき。

### Hyrum's Law が削除を難しくする

十分なユーザーがいれば、観測可能な挙動はすべて依存される――バグ、タイミングの癖、未文書化の副作用を含む。だから廃止予定は発表ではなく能動的マイグレーションを要する。置換物が複製しない挙動にユーザーが依存しているとき、「ただ切り替えて」は通らない。

### 廃止予定計画は設計時に始まる

新しいものを作るときに問え: 「3年後にどうやって取り除く?」 クリーンなインターフェース、フィーチャーフラグ、最小サーフェスで設計されたシステムは、実装詳細を至る所に漏らすシステムより廃止予定しやすい。

## 廃止予定の決定

廃止予定前に次の質問に答える:

```
1. このシステムはまだ固有の価値を提供するか?
   → Yesなら維持。Noなら続行。

2. 何人のユーザー・利用者が依存するか?
   → マイグレーション範囲を定量化。

3. 置換物は存在するか?
   → Noならまず置換物を作る。代替なしに廃止予定しない。

4. 各利用者のマイグレーションコストは?
   → 自動化できるならやる。手動で高コストなら維持コストと比較。

5. 廃止予定しないメンテコストは?
   → セキュリティリスク、エンジニア時間、複雑さの機会コスト。
```

## 強制的 vs アドバイザリ廃止予定

| タイプ | 使うとき | メカニズム |
|------|-------------|-----------|
| **アドバイザリ** | マイグレーションが任意、古いシステムが安定 | 警告、ドキュメント、推奨。ユーザーは自分のタイミングでマイグレート。 |
| **強制的** | 古いシステムにセキュリティ問題、進行をブロック、維持コストが持続不能 | 固定期限。日付Xまでに古いシステムが削除される。マイグレーションツール提供。 |

**デフォルトはアドバイザリ。** 維持コストやリスクがマイグレーションを強制するに足るときだけ強制的を使う。強制的廃止予定はマイグレーションツール、ドキュメント、サポート提供を要する――期限発表だけでは不可。

## マイグレーションプロセス

### ステップ1: 置換物を作る

動作する代替物なしに廃止予定しない。置換物は:

- 古いシステムのすべての重要ユースケースをカバー
- ドキュメントとマイグレーションガイドを持つ
- 本番で証明済み（「理論上優れている」ではなく）

### ステップ2: 告知と文書化

```markdown
## 廃止予定通知: OldService

**ステータス:** 2025-03-01 から廃止予定
**置換:** NewService（下のマイグレーションガイド参照）
**削除日:** アドバイザリ――固定期限なし
**理由:** OldServiceは手動スケーリングを要し観測性に欠ける。
          NewServiceは両方自動で処理。

### マイグレーションガイド
1. `import { client } from 'old-service'` を `import { client } from 'new-service'` に置換
2. 設定を更新（下の例参照）
3. マイグレーション検証スクリプト実行: `npx migrate-check`
```

### ステップ3: 段階的マイグレーション

利用者を一度に全部ではなく1つずつマイグレートする。各利用者について:

```
1. 廃止予定システムとの全接点を特定
2. 置換物を使うよう更新
3. 挙動一致を検証（テスト、統合チェック）
4. 古いシステムへの参照を削除
5. リグレッションがないことを確認
```

**Churn Rule:** 廃止予定されるインフラを所有するなら、ユーザーのマイグレーション責任を負う――またはマイグレーション不要な後方互換更新を提供する。廃止予定を発表してユーザーに任せない。

### ステップ4: 古いシステムの削除

全利用者がマイグレート後にのみ:

```
1. 使用ゼロを検証（メトリクス、ログ、依存解析）
2. コードを削除
3. 関連テスト、ドキュメント、設定を削除
4. 廃止予定通知を削除
5. 祝う――コード削除は達成
```

## マイグレーションパターン

### Stranglerパターン

古いと新しいシステムを並行稼働。古いから新しいへ段階的にトラフィックをルート。古いシステムがトラフィック0%を扱うようになったら削除。

```
Phase 1: 新システム 0%、古 100%
Phase 2: 新システム 10%（カナリア）
Phase 3: 新システム 50%
Phase 4: 新システム 100%、古がアイドル
Phase 5: 古システム削除
```

### Adapterパターン

古いインターフェースから新実装への呼び出しを変換するアダプタを作る。バックエンドをマイグレート中も利用者は古いインターフェースを使い続ける。

```typescript
// アダプタ: 古いインターフェース、新実装
class LegacyTaskService implements OldTaskAPI {
  constructor(private newService: NewTaskService) {}

  // 古いメソッドシグネチャ、新実装に委譲
  getTask(id: number): OldTask {
    const task = this.newService.findById(String(id));
    return this.toOldFormat(task);
  }
}
```

### フィーチャーフラグマイグレーション

フラグを使って利用者を古いシステムから新しいシステムへ1つずつ切り替え:

```typescript
function getTaskService(userId: string): TaskService {
  if (featureFlags.isEnabled('new-task-service', { userId })) {
    return new NewTaskService();
  }
  return new LegacyTaskService();
}
```

## ゾンビコード

ゾンビコードは誰も所有しないが皆が依存するコード。活発にメンテされず、明確な所有者がなく、セキュリティ脆弱性と互換性問題を蓄積する。兆候:

- 6ヶ月以上コミットがないが活発な利用者が存在
- 割り当てられたメンテナやチームがない
- 誰も直さない失敗テスト
- 誰も更新しない既知の脆弱性を持つ依存
- もう存在しないシステムを参照するドキュメント

**対応:** 所有者を割り当てて適切に維持するか、具体的マイグレーション計画で廃止予定する。ゾンビコードは宙ぶらりんで居続けられない――投資か削除のどちらか。

## よくある言い訳

| 言い訳 | 現実 |
|---|---|
| 「まだ動くのに、なぜ削除?」 | 誰もメンテしない動くコードはセキュリティ負債と複雑さを蓄積する。メンテコストは静かに育つ。 |
| 「後で必要になるかも」 | 後で必要になったら作り直せる。「念のため」未使用コードを残すのは作り直しより高い。 |
| 「マイグレーションが高すぎる」 | マイグレーションコストと2〜3年の維持コストを比較。長期的にマイグレーションが安い。 |
| 「新システム完成後に廃止予定する」 | 廃止予定計画は設計時に始まる。新システム完成時には新しい優先事項がある。今計画を。 |
| 「ユーザーが自分でマイグレートする」 | しない。ツール、ドキュメント、インセンティブを提供――または自分でマイグレートする（Churn Rule）。 |
| 「両システムを無期限に維持できる」 | 同じことをする2つのシステムは維持、テスト、ドキュメント、オンボーディングが倍コスト。 |

## レッドフラグ

- 置換物のない廃止予定システム
- マイグレーションツールやドキュメントのない廃止予定発表
- 何年もアドバイザリのまま進まない「ソフト」廃止予定
- 所有者なしで活発な利用者のあるゾンビコード
- 廃止予定システムに新機能を追加（代わりに置換物に投資）
- 現使用量を計測しない廃止予定
- アクティブ利用者ゼロを検証せずコード削除

## 検証

廃止予定完了後:

- [ ] 置換物が本番実証済みで重要ユースケースすべてをカバー
- [ ] 具体的ステップと例付きマイグレーションガイドが存在
- [ ] すべての活発利用者がマイグレート済み（メトリクス/ログで検証）
- [ ] 古いコード、テスト、ドキュメント、設定が完全削除
- [ ] コードベースに廃止予定システムへの参照が残っていない
- [ ] 廃止予定通知は削除（目的を果たした）
