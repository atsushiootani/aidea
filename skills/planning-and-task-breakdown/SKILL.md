# 計画とタスク分解

## 概要

作業を小さく、検証可能なタスクに分解し、明示的な受入基準をつける。良いタスク分解は、作業を確実に完了するエージェントと、絡み合った混乱を生むエージェントの差。すべてのタスクは、1つの集中セッションで実装、テスト、検証できるほど小さくあるべき。

## 使うタイミング

- スペックがあり、実装可能な単位に分解する必要がある
- タスクが大きすぎたり曖昧すぎたりして始められない
- 作業を複数のエージェントやセッションに並列化する必要がある
- 人間にスコープを伝える必要がある
- 実装順序が明らかでない

**使わないとき:** スコープが明らかな単一ファイル変更、またはスペックに既に良く定義されたタスクがある場合。

## 計画プロセス

### ステップ1: プランモードに入る

コードを書く前に、読み取り専用モードで動作:

- スペックと関連するコードベースセクションを読む
- 既存のパターンと慣習を識別
- コンポーネント間の依存関係をマップ
- リスクと未知事項を記録

**計画中はコードを書かない。** 出力は計画文書であり、実装ではない。

### ステップ2: 依存関係グラフを識別

何が何に依存するかをマップ:

```
データベーススキーマ
    │
    ├── API モデル/型
    │       │
    │       ├── API エンドポイント
    │       │       │
    │       │       └── フロントエンド API クライアント
    │       │               │
    │       │               └── UI コンポーネント
    │       │
    │       └── バリデーションロジック
    │
    └── シードデータ / マイグレーション
```

実装順序は依存関係グラフをボトムアップで辿る: 基盤を先に作る。

### ステップ3: 垂直にスライスする

全データベースを作り、次に全API、次に全UI…ではなく、1つの完全な機能パスを一度に作る:

**悪い（水平スライス）:**
```
タスク1: データベーススキーマ全体を構築
タスク2: すべての API エンドポイントを構築
タスク3: すべての UI コンポーネントを構築
タスク4: すべてを接続
```

**良い（垂直スライス）:**
```
タスク1: ユーザーがアカウントを作成できる（登録用のスキーマ + API + UI）
タスク2: ユーザーがログインできる（認証スキーマ + API + ログイン UI）
タスク3: ユーザーがタスクを作成できる（タスクスキーマ + API + 作成 UI）
タスク4: ユーザーがタスク一覧を閲覧できる（クエリ + API + 一覧表示 UI）
```

各垂直スライスは動作する、テスト可能な機能を届ける。

### ステップ4: タスクを書く

各タスクはこの構造に従う:

```markdown
## タスク [N]: [短い説明的タイトル]

**説明:** このタスクが何を達成するかを 1 段落で説明する。

**受入基準:**
- [ ] [具体的でテスト可能な条件]
- [ ] [具体的でテスト可能な条件]

**検証方法:**
- [ ] テスト通過: `npm test -- --grep "feature-name"`
- [ ] ビルド成功: `npm run build`
- [ ] 手動チェック: [何を確認するかの説明]

**依存:** [依存するタスク番号、または「なし」]

**変更が予想されるファイル:**
- `src/path/to/file.ts`
- `tests/path/to/test.ts`

**見積りスコープ:** [Small: 1-2 ファイル | Medium: 3-5 ファイル | Large: 5+ ファイル]
```

### ステップ5: 順序付けとチェックポイント

タスクを以下のように配置:

1. 依存関係が満たされる（基盤を先に作る）
2. 各タスクがシステムを動作状態に残す
3. 2-3タスクごとに検証チェックポイントがある
4. 高リスクタスクが早い（早く失敗する）

明示的なチェックポイントを追加:

```markdown
## チェックポイント: タスク 1〜3 の後
- [ ] すべてのテストが通過
- [ ] アプリケーションがエラーなくビルドできる
- [ ] 中核のユーザーフローがエンドツーエンドで動作
- [ ] 進める前に人間とレビュー
```

## タスクサイジングガイドライン

| サイズ | ファイル | スコープ | 例 |
|------|-------|-------|---------|
| **XS** | 1 | 単一関数または設定変更 | バリデーションルール追加 |
| **S** | 1-2 | 1コンポーネントまたはエンドポイント | 新APIエンドポイント追加 |
| **M** | 3-5 | 1機能スライス | ユーザー登録フロー |
| **L** | 5-8 | マルチコンポーネント機能 | フィルタリングとページネーション付き検索 |
| **XL** | 8+ | **大きすぎ — さらに分解する** | — |

タスクがLより大きければ、さらに小さく分解するべき。エージェントはSとMのタスクで最もパフォーマンスを発揮する。

**タスクをさらに分解するタイミング:**
- 1つの集中セッション以上（おおむね2時間以上のエージェント作業）かかる
- 受入基準を3つ以下の箇条書きで記述できない
- 2つ以上の独立したサブシステム（例: 認証と課金）に触れる
- タスクタイトルに「and」を書きそうになる（2つのタスクの兆候）

## 計画文書テンプレート

```markdown
# 実装計画: [機能/プロジェクト名]

## 概要
[作るものを 1 段落で要約]

## アーキテクチャ決定
- [主要な決定 1 とその根拠]
- [主要な決定 2 とその根拠]

## タスクリスト

### フェーズ1: 基盤
- [ ] タスク1: ...
- [ ] タスク2: ...

### チェックポイント: 基盤
- [ ] テスト通過、ビルド成功

### フェーズ2: 中核機能
- [ ] タスク3: ...
- [ ] タスク4: ...

### チェックポイント: 中核機能
- [ ] エンドツーエンドのフローが動作

### フェーズ3: 仕上げ
- [ ] タスク5: ...
- [ ] タスク6: ...

### チェックポイント: 完了
- [ ] すべての受入基準を満たす
- [ ] レビュー準備完了

## リスクと緩和策
| リスク | 影響 | 緩和策 |
|------|--------|------------|
| [リスク] | [高/中/低] | [戦略] |

## オープンな疑問
- [人間の入力が必要な疑問]
```

## 並列化の機会

複数エージェントまたはセッションが利用可能な場合:

- **安全に並列化可能:** 独立した機能スライス、既に実装された機能のテスト、ドキュメント
- **順次である必要あり:** データベースマイグレーション、共有状態変更、依存チェーン
- **調整が必要:** APIコントラクトを共有する機能（先にコントラクトを定義してから並列化）

## よくある言い訳

| 言い訳 | 現実 |
|---|---|
| "進めながら考える" | それが絡み合った混乱と手戻りの原因。10分の計画が数時間を節約。 |
| "タスクは明らか" | それでも書き留める。明示的なタスクは隠れた依存関係や忘れられたエッジケースを表面化する。 |
| "計画はオーバーヘッド" | 計画がタスク。計画なしの実装は単なるタイピング。 |
| "全部頭に入れておける" | コンテキストウィンドウは有限。書かれた計画はセッション境界と圧縮を生き延びる。 |

## レッドフラグ

- 書かれたタスクリストなしで実装を始める
- 受入基準なく「機能を実装」とだけ書かれたタスク
- 計画に検証ステップがない
- 全タスクがXLサイズ
- タスク間にチェックポイントがない
- 依存順序が考慮されていない

## 検証

実装を始める前に確認:

- [ ] すべてのタスクに受入基準がある
- [ ] すべてのタスクに検証ステップがある
- [ ] タスクの依存関係が識別され正しく順序付けられている
- [ ] どのタスクもおよそ5ファイル以上に触れない
- [ ] 主要フェーズ間にチェックポイントが存在する
- [ ] 人間が計画をレビュー・承認した
