# 増分実装

## 概要

薄い垂直スライスで作る — 1つの部分を実装し、テストし、検証してから拡張。機能全体を1回のパスで実装するのを避ける。各増分はシステムを動作する、テスト可能な状態に残すべき。これが大きな機能を扱いやすくする実行規律。

## 使うタイミング

- 複数ファイル変更を実装するとき
- タスク分解から新機能を作るとき
- 既存コードのリファクタ
- テスト前に100行以上のコードを書きたくなる時

**使わないとき:** スコープが既に最小限の単一ファイル・単一関数の変更。

## 増分サイクル

```
┌──────────────────────────────────────┐
│                                      │
│   実装 ──→ テスト ──→ 検証 ─────┐    │
│    ▲                            │    │
│    └────── コミット ◄───────────┘    │
│              │                       │
│              ▼                       │
│          次のスライスへ              │
│                                      │
└──────────────────────────────────────┘
```

各スライスで:

1. **Implement** — 機能の最小の完全な1片を実装
2. **Test** — テストスイートを実行（なければテストを書く）
3. **Verify** — スライスが期待通りに動作することを確認（テストパス、ビルド成功、手動チェック）
4. **Commit** — 記述的なメッセージで進捗を保存（原子的コミットガイダンスは `git-workflow-and-versioning` 参照）
5. **次のスライスへ** — やり直さず、持ち越す

## スライス戦略

### 垂直スライス（推奨）

スタックを貫く1つの完全なパスを作る:

```
スライス1: タスクを作成する (DB + API + 基本 UI)
    → テスト通過、ユーザーが UI 経由でタスクを作成できる

スライス2: タスク一覧 (クエリ + API + UI)
    → テスト通過、ユーザーが自分のタスクを閲覧できる

スライス3: タスク編集 (更新 + API + UI)
    → テスト通過、ユーザーがタスクを変更できる

スライス4: タスク削除 (削除 + API + UI + 確認)
    → テスト通過、CRUD 完了
```

各スライスが動作するエンドツーエンドの機能を届ける。

### コントラクトファーストスライス

バックエンドとフロントエンドを並列に開発する必要があるとき:

```
スライス0: API コントラクトを定義（型、インターフェース、OpenAPI 仕様）
スライス1a: コントラクトに沿ってバックエンドを実装 + API テスト
スライス1b: コントラクトに合致するモックデータでフロントエンドを実装
スライス2: 統合してエンドツーエンドでテスト
```

### リスクファーストスライス

最もリスキーまたは不確実な部分を先に取り組む:

```
スライス1: WebSocket 接続が動作することを証明（最大リスク）
スライス2: 実証済みの接続上にリアルタイムタスク更新を構築
スライス3: オフラインサポートと再接続を追加
```

スライス1が失敗したら、スライス2と3に投資する前に発見できる。

## 実装ルール

### ルール0: シンプルさ優先

コードを書く前に問う: 「動作する最もシンプルなものは何か？」

コードを書いた後、以下のチェックに対してレビュー:
- 少ない行数でできるか？
- これらの抽象化は複雑さに見合うか？
- スタッフエンジニアが見たら「なぜ単に…しないの？」と言うか？
- 仮想的な将来要件のために作っていないか、現在のタスクのためか？

```
シンプルさチェック:
✗ 1 つの通知のためにミドルウェアパイプライン付き汎用 EventBus
✓ シンプルな関数呼び出し

✗ 似た 2 つのコンポーネントのために抽象ファクトリーパターン
✓ 共有ユーティリティを持つ素直な 2 つのコンポーネント

✗ 3 つのフォームのために設定駆動フォームビルダー
✓ 3 つのフォームコンポーネント
```

似たコード3行は早すぎる抽象化に勝る。素朴で明らかに正しいバージョンを先に実装。正しさがテストで証明されてから最適化する。

### ルール0.5: スコープ規律

タスクが要求するものだけに触れる。

以下はNG:
- 変更に隣接するコードを「クリーンアップ」
- 変更していないファイルのインポートをリファクタ
- 完全に理解していないコメントを削除
- スペックにない機能を「便利そう」という理由で追加
- 読んでいるだけのファイルで構文を近代化

タスクスコープ外で改善に値するものに気づいたら、記録する — 直さない:

```
気づいたが触らない:
- src/utils/format.ts に未使用の import がある（このタスクとは無関係）
- 認証ミドルウェアのエラーメッセージを改善できる（別タスク）
→ これらのタスクを作成しますか?
```

### ルール1: 一度に1つのこと

各増分は論理的に1つのことを変える。関心を混ぜない:

**悪い:** 1つのコミットで新コンポーネント追加、既存コンポーネントのリファクタ、ビルド設定更新。

**良い:** 3つの別々のコミット — 各変更に1つ。

### ルール2: コンパイル可能に保つ

各増分の後、プロジェクトはビルドでき、既存テストはパスしなければならない。スライス間でコードベースを壊れた状態に残さない。

### ルール3: 不完全機能のためのフィーチャーフラグ

機能がユーザー準備完了でないが増分をマージする必要があるとき:

```typescript
// 開発中の機能のためのフィーチャーフラグ
const ENABLE_TASK_SHARING = process.env.FEATURE_TASK_SHARING === 'true';

if (ENABLE_TASK_SHARING) {
  // 新しい共有 UI
}
```

これにより不完全な作業を露出せずに小さい増分をメインブランチにマージできる。

### ルール4: 安全なデフォルト

新しいコードは安全で保守的な振る舞いをデフォルトにするべき:

```typescript
// 安全: デフォルトで無効、オプトイン
export function createTask(data: TaskInput, options?: { notify?: boolean }) {
  const shouldNotify = options?.notify ?? false;
  // ...
}
```

### ルール5: ロールバックフレンドリー

各増分は独立してリバート可能であるべき:

- 追加的変更（新ファイル、新関数）はリバートが容易
- 既存コードへの変更は最小かつフォーカスされるべき
- データベースマイグレーションには対応するロールバックマイグレーションがあるべき
- 同じコミットで何かを削除して置き換えるのは避ける — 分離する

## エージェントとの作業

増分的に実装するようエージェントに指示するとき:

```
「計画のタスク3を実装しよう。

まずデータベーススキーマの変更と API エンドポイントだけ着手して。
UI はまだ触らないで — それは次の増分でやる。

実装後、`npm test` と `npm run build` を実行して
何も壊れていないことを検証して。」
```

各増分のスコープ内とスコープ外を明示的に。

## 増分チェックリスト

各増分の後、検証:

- [ ] 変更は1つのことを完全にやる
- [ ] 既存テストすべてがパス（`npm test`）
- [ ] ビルドが成功（`npm run build`）
- [ ] 型チェックがパス（`npx tsc --noEmit`）
- [ ] リンティングがパス（`npm run lint`）
- [ ] 新機能が期待通りに動作
- [ ] 記述的なメッセージで変更がコミットされた

## よくある言い訳

| 言い訳 | 現実 |
|---|---|
| "最後に全部テストする" | バグは複合する。スライス1のバグはスライス2-5を間違いにする。各スライスをテスト。 |
| "一度にやる方が速い" | 壊れた時に500行の変更のどれが原因か見つけられなくなるまで*感じるだけ*。 |
| "これらの変更は別々にコミットするには小さすぎる" | 小さなコミットは無料。大きなコミットはバグを隠しロールバックを痛ましくする。 |
| "フィーチャーフラグは後で追加する" | 機能が不完全ならユーザー可視であるべきではない。今フラグを追加。 |
| "このリファクタは含めるのに十分小さい" | 機能と混ざったリファクタは両方をレビュー・デバッグしにくくする。分離。 |

## レッドフラグ

- テストを実行せずに100行以上のコードを書いている
- 1つの増分に複数の無関係な変更
- 「ついでにこれも追加しちゃおう」スコープ拡大
- 速さのためにテスト・検証ステップをスキップ
- 増分間でビルドまたはテストが壊れている
- 大きな未コミット変更が蓄積
- 3番目のユースケースが要求する前に抽象化を作る
- 「ついでに」タスクスコープ外のファイルに触れる
- 一度限りの操作のために新しいユーティリティファイルを作る

## 検証

タスクの全増分を完了した後:

- [ ] 各増分が個別にテストされ、コミットされた
- [ ] 完全なテストスイートがパス
- [ ] ビルドがクリーン
- [ ] 機能がスペック通りエンドツーエンドで動作
- [ ] 未コミット変更が残っていない
