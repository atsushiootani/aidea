# コードレビューと品質

## 概要

多次元のコードレビューと品質ゲート。すべての変更はマージ前にレビューする――例外なし。レビューは5つの軸をカバーする: 正しさ、読みやすさ、アーキテクチャ、セキュリティ、パフォーマンス。

**承認基準:** 完璧でなくとも、コード全体の健全性を確実に改善する変更なら承認する。完璧なコードは存在しない――目標は継続的改善。自分が書くやり方と完全に一致しないからといってブロックしないこと。コードベースを改善し、プロジェクトの慣習に従っているなら承認する。

## 使うとき

- PRや変更をマージする前
- 機能実装が完了したとき
- 別のエージェントやモデルが書いたコードを評価するとき
- 既存コードをリファクタするとき
- バグ修正後（修正とリグレッションテストの両方をレビュー）

## 5軸レビュー

すべてのレビューは次の次元でコードを評価する:

### 1. 正しさ

コードはそれが主張することをしているか?

- 仕様またはタスク要件と一致しているか?
- エッジケース（null、空、境界値）が処理されているか?
- エラーパスが処理されているか（ハッピーパスだけでなく）?
- すべてのテストが通るか? テストは正しいことをテストしているか?
- オフバイワン、レースコンディション、状態不整合はないか?

### 2. 読みやすさとシンプルさ

他のエンジニア（やエージェント）が作者の説明なしでこのコードを理解できるか?

- 名前は説明的で、プロジェクト慣習と一致しているか?（文脈なしの `temp`, `data`, `result` はNG）
- 制御フローは素直か?（ネストされた三項演算子、深いコールバックを避ける）
- コードは論理的に整理されているか?（関連コードはまとまっているか、モジュール境界は明確か）
- 簡略化すべき「巧妙な」トリックはないか?
- **もっと少ない行数でできないか?**（100行で足りるところに1000行は失敗）
- **抽象化は複雑さに見合う価値があるか?**（3回目の使用まで一般化しない）
- 非自明な意図を明確にするコメントが役立つか?（当たり前のコードにはコメントしない）
- デッドコードの残骸はないか: noop変数（`_unused`）、後方互換シム、`// removed` コメントなど?

### 3. アーキテクチャ

この変更はシステムの設計に適合しているか?

- 既存パターンに従うか、新しいパターンを導入するか? 新しいなら正当化されているか?
- クリーンなモジュール境界を維持しているか?
- 共有すべきコード重複はないか?
- 依存の方向は正しいか?（循環依存なし）
- 抽象化レベルは適切か?（過剰設計、過密結合でない）

### 4. セキュリティ

詳細なセキュリティガイダンスは `security-and-hardening` を参照。この変更は脆弱性を導入するか?

- ユーザー入力は検証・サニタイズされているか?
- シークレットはコード、ログ、バージョン管理から外されているか?
- 認証/認可は必要な箇所で確認されているか?
- SQLクエリはパラメータ化されているか?（文字列結合なし）
- 出力はXSSを防ぐためエンコードされているか?
- 依存は信頼できるソースで既知の脆弱性がないか?
- 外部ソース（API、ログ、ユーザーコンテンツ、設定ファイル）からのデータは信頼できないものとして扱われているか?
- 外部データフローはロジックやレンダリングで使用する前に境界で検証されているか?

### 5. パフォーマンス

詳細なプロファイリングと最適化は `performance-optimization` を参照。この変更はパフォーマンス問題を導入するか?

- N+1クエリパターンは?
- 無制限ループや制約のないデータフェッチは?
- 非同期にすべき同期処理は?
- UIコンポーネントの不要な再レンダリングは?
- リストエンドポイントでページネーションが欠けていないか?
- ホットパスで大きなオブジェクトを作っていないか?

## 変更のサイズ

小さく焦点を絞った変更はレビューしやすく、マージも速く、デプロイも安全。目指すサイズ:

```
~100行の変更    → 良い。一度にレビュー可能
~300行の変更    → 単一論理変更なら許容
~1000行の変更   → 大きすぎ。分割する
```

**「1つの変更」とは:** 1つのことに対処し、関連テストを含み、サブミット後もシステムを機能させる、自己完結した単一の変更。機能の一部――機能全体ではない。

**変更が大きすぎる場合の分割戦略:**

| 戦略 | 方法 | いつ |
|----------|-----|------|
| **スタック** | 小さな変更をサブミット、それを基に次を始める | 順次依存 |
| **ファイルグループ別** | 異なるレビュアーが必要なグループで分ける | 横断的関心事 |
| **水平** | 共有コード/スタブを先に、次に利用者 | レイヤードアーキテクチャ |
| **垂直** | 機能をより小さなフルスタックスライスに分ける | 機能開発 |

**大きな変更が許容される場合:** 完全なファイル削除や自動リファクタリングなど、レビュアーが意図だけを検証すればよい場合。

**リファクタリングと機能作業を分離する。** 既存コードをリファクタしつつ新しい挙動を追加する変更は2つの変更――別々にサブミットする。小さなクリーンアップ（変数リネーム）はレビュアーの裁量で含めてよい。

## 変更の説明

すべての変更にはバージョン管理履歴内で単独で成り立つ説明が必要。

**1行目:** 短く、命令形、自己完結。「FizzBuzz RPC を削除する」であって「FizzBuzz RPC を削除中」ではない。履歴検索する人が差分を読まずに変更を理解できる程度に情報豊富でなければならない。

**本文:** 何が変わり、なぜか。コンテキスト、決定、コード自体に見えない理由を含める。関連するバグ番号、ベンチマーク結果、設計ドキュメントへリンクする。アプローチの欠点があれば認める。

**アンチパターン:** 「バグ修正」「ビルド修正」「パッチを追加」「コードをAからBへ移動」「フェーズ1」「便利関数を追加」。

## レビュープロセス

### ステップ1: コンテキストを理解

コードを見る前に意図を理解する:

```
- この変更は何を達成しようとしているか?
- どの仕様やタスクを実装しているか?
- 期待される挙動の変化は?
```

### ステップ2: テストを先にレビュー

テストは意図とカバレッジを示す:

```
- 変更に対するテストが存在するか?
- 挙動をテストしているか?（実装詳細ではなく）
- エッジケースはカバーされているか?
- テスト名は説明的か?
- コードが変わったらリグレッションを捕まえられるか?
```

### ステップ3: 実装をレビュー

5軸を念頭にコードを読み進める:

```
変更された各ファイルについて:
1. 正しさ: このコードはテストが言うとおりのことをしているか?
2. 読みやすさ: 助けなしで理解できるか?
3. アーキテクチャ: システムに適合するか?
4. セキュリティ: 脆弱性はないか?
5. パフォーマンス: ボトルネックはないか?
```

### ステップ4: 指摘を分類

すべてのコメントに重大度ラベルを付け、必須と任意を明確にする:

| プレフィックス | 意味 | 作者のアクション |
|--------|---------|---------------|
| *(プレフィックスなし)* | 必須の変更 | マージ前に対処 |
| **Critical:** | マージブロック | セキュリティ脆弱性、データ損失、機能破綻 |
| **Nit:** | 微細、任意 | 作者は無視してよい――フォーマット、スタイル好み |
| **Optional:** / **Consider:** | 提案 | 検討する価値があるが必須ではない |
| **FYI** | 情報のみ | アクション不要――将来の参考 |

これにより作者がすべてのフィードバックを必須扱いして任意提案に時間を浪費するのを防ぐ。

### ステップ5: 検証を検証する

作者の検証ストーリーを確認:

```
- どのテストを実行したか?
- ビルドは通ったか?
- 手動でテストしたか?
- UI変更のスクリーンショットはあるか?
- ビフォー/アフター比較はあるか?
```

## マルチモデルレビューパターン

異なるモデルを異なるレビュー視点に使う:

```
モデルAがコードを書く
    │
    ▼
モデルBが正しさとアーキテクチャをレビュー
    │
    ▼
モデルAがフィードバックに対処
    │
    ▼
人間が最終判断
```

単一モデルが見逃す問題をキャッチできる――モデルには異なる盲点がある。

**レビューエージェント用プロンプト例:**
```
このコード変更を正しさ、セキュリティ、プロジェクト慣習の遵守について
レビューせよ。仕様は[X]と述べている。変更は[Y]すべき。
問題は Critical、Important、Suggestion でフラグせよ。
```

## デッドコード衛生

リファクタリングや実装変更後、孤立コードをチェック:

1. 到達不能または未使用になったコードを特定
2. 明示的にリストアップ
3. **削除前に尋ねる:** 「これらの未使用要素を削除しますか: [リスト]?」

デッドコードを放置しない――将来の読者とエージェントを混乱させる。でも確信がないものを黙って削除しない。疑わしければ尋ねる。

```
デッドコードを特定:
- formatLegacyDate() in src/utils/date.ts — formatDate() に置き換え済み
- OldTaskCard component in src/components/ — TaskCard に置き換え済み
- LEGACY_API_URL constant in src/config.ts — 参照なし
→ これらを削除しても安全?
```

## レビュー速度

遅いレビューはチーム全体をブロックする。レビューへのコンテキストスイッチコストは、他者に課される待機コストより小さい。

- **1営業日以内に応答する** ――これは最大、目標ではない
- **理想のケイデンス:** レビュー依頼到着直後に応答、深い集中コーディング中を除く。典型的な変更は1日で複数回のレビューラウンドを完了すべき
- **素早い承認より素早い個別応答を優先する。** 複数ラウンドが必要でも素早いフィードバックがフラストレーションを減らす
- **大きな変更:** 巨大な変更セットをレビューするより、作者に分割を依頼

## 意見の相違の処理

レビュー争いを解決する際は次の階層を適用:

1. **技術的事実とデータ**が意見と好みを上回る
2. **スタイルガイド**はスタイル事項の絶対的権威
3. **ソフトウェア設計**は個人的好みでなくエンジニアリング原則で評価する
4. **コードベース一貫性**は全体の健全性を損なわない限り許容される

**「後でクリーンアップする」を受け入れない。** 経験上、先延ばしのクリーンアップは稀にしか実現しない。真の緊急事態でない限りサブミット前のクリーンアップを要求する。周辺問題をこの変更で対処できない場合、自己アサインのバグ登録を要求する。

## レビューでの誠実さ

コードをレビューする際――自分、別エージェント、人間の誰が書いたにせよ:

- **ラバースタンプしない。** 証拠なしの "LGTM" は誰の役にも立たない。
- **本当の問題を和らげない。** プロダクションに到達するバグを「軽微な懸念かも」と言うのは不誠実。
- **可能なら問題を定量化。** 「このN+1クエリはリストの項目毎に~50ms追加する」は「遅いかも」より良い。
- **明らかな問題のあるアプローチに反論する。** レビューでの迎合は失敗モード。実装に問題があれば直接言い、代替を提案する。
- **オーバーライドを潔く受け入れる。** 作者が全コンテキストを持ち反対するなら、その判断に従う。人ではなくコードにコメント――個人批判はコード自体の話に再構成する。

## 依存規律

コードレビューの一部は依存レビュー:

**依存を追加する前に:**
1. 既存スタックで解決できるか?（しばしば可能）
2. 依存はどれほど大きいか?（バンドル影響をチェック）
3. 活発にメンテされているか?（最新コミット、オープンIssue）
4. 既知の脆弱性があるか?（`npm audit`）
5. ライセンスは?（プロジェクトと互換でなければならない）

**ルール:** 新規依存より標準ライブラリと既存ユーティリティを優先。すべての依存は負債。

## レビューチェックリスト

```markdown
## レビュー: [PR/変更タイトル]

### コンテキスト
- [ ] この変更が何をするか、なぜかを理解している

### 正しさ
- [ ] 仕様/タスク要件と一致
- [ ] エッジケース処理
- [ ] エラーパス処理
- [ ] テストが変更を適切にカバー

### 読みやすさ
- [ ] 名前が明確で一貫
- [ ] ロジックが素直
- [ ] 不要な複雑さなし

### アーキテクチャ
- [ ] 既存パターンに従う
- [ ] 不要な結合や依存なし
- [ ] 適切な抽象化レベル

### セキュリティ
- [ ] コード内にシークレットなし
- [ ] 境界で入力検証
- [ ] インジェクション脆弱性なし
- [ ] 認証チェック配置
- [ ] 外部データソースを信頼できないものとして扱う

### パフォーマンス
- [ ] N+1パターンなし
- [ ] 無制限処理なし
- [ ] リストエンドポイントにページネーション

### 検証
- [ ] テスト通過
- [ ] ビルド成功
- [ ] 手動検証実施（該当時）

### 判定
- [ ] **承認** ――マージ可能
- [ ] **変更要求** ――問題に対処が必要
```

## よくある言い訳

| 言い訳 | 現実 |
|---|---|
| 「動くからOK」 | 読みにくい、安全でない、設計がおかしい動くコードは複合する負債を生む。 |
| 「自分が書いたから正しいとわかる」 | 作者は自分の前提に盲目。すべての変更は別の目の恩恵を受ける。 |
| 「後でクリーンアップする」 | 「後で」は来ない。レビューは品質ゲート――使え。マージ前に、後ではなく。 |
| 「AI生成コードはたぶん大丈夫」 | AIコードはより精査が必要、少なくではない。間違っていても自信満々でもっともらしい。 |
| 「テストが通るからよい」 | テストは必要だが十分ではない。アーキテクチャ問題、セキュリティ、読みやすさを捕捉しない。 |

## レッドフラグ

- レビューなしでマージされるPR
- テスト通過だけをチェックするレビュー（他の軸を無視）
- 実際のレビュー証拠のない "LGTM"
- セキュリティ重視レビューのないセキュリティ関連変更
- 「大きすぎて適切にレビューできない」PR（分割する）
- バグ修正PRにリグレッションテストなし
- 重大度ラベルのないレビューコメント――必須か任意か不明
- 「後で直す」を受け入れる――起こらない

## 検証

レビュー完了後:

- [ ] すべてのCriticalが解決
- [ ] すべてのImportantが解決または正当化された延期
- [ ] テスト通過
- [ ] ビルド成功
- [ ] 検証ストーリーが記録されている（何が変わり、どう検証したか）
