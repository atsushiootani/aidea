# スキルの構造（Skill Anatomy）

このドキュメントは agent-skills のスキルファイルの構造とフォーマットを説明します。新しいスキルを寄稿するとき、または既存のスキルを理解するときのガイドとして使ってください。

## ファイルの配置

各スキルは `skills/` 配下に独自のディレクトリを持ちます。

```
skills/
  skill-name/
    SKILL.md          # 必須: スキル定義
    supporting-file.md # 任意: オンデマンドで読み込まれる補助資料
```

## SKILL.md フォーマット

### フロントマター（必須）

```yaml
---
name: skill-name-with-hyphens
description: Brief statement of what the skill does. Use when [specific trigger conditions].
---
```

**ルール:**
- `name`: 小文字ハイフン区切り。ディレクトリ名と一致させること。
- `description`: スキルが何をするか（三人称）から始め、その後にトリガー条件を書く。*何を*と*いつ*の両方を含めること。最大 1024 文字。

**なぜ重要か:** エージェントは description を読んでスキルを発見します。description はシステムプロンプトに注入されるため、エージェントに対して「何を提供するか」と「いつ有効化するか」の両方を伝える必要があります。ワークフローを要約してはいけません — description にプロセスのステップが含まれていると、エージェントはスキル本体を読まずに要約に従ってしまう可能性があります。

### 標準セクション

```markdown
# スキルタイトル

## 概要
このスキルが何をして、なぜ重要なのかを 1〜2 文で説明する。

## 使用タイミング
- トリガー条件（症状、タスクの種類）の箇条書き
- 使わない場面（除外条件）

## [コアプロセス / ワークフロー / ステップ]
番号付きステップまたはフェーズに分解したメインのワークフロー。
役立つ場面ではコード例を含める。
判断ポイントがある場所では（ASCII の）フローチャートを使う。

## [具体的な手法 / パターン]
特定のシナリオに対する詳細なガイダンス。
コード例、テンプレート、設定など。

## よくある合理化
| 合理化 | 現実 |
|---|---|
| エージェントがステップをスキップする言い訳 | その言い訳がなぜ間違っているか |

## レッドフラグ
- スキルが守られていないことを示す行動パターン
- レビュー中に注意すべきこと

## 検証
スキルのプロセス完了後に次を確認する:
- [ ] 終了条件のチェックリスト
- [ ] 証拠要件
```

## 各セクションの目的

### Overview
スキルの「エレベーターピッチ」。「このスキルは何をするのか、なぜエージェントは従うべきか」に答えるものです。

### When to Use
エージェントや人間が、現在のタスクにこのスキルが適用されるかを判断するのに役立ちます。肯定的なトリガー（「X のときに使う」）と除外条件（「Y には使わない」）の両方を含めます。

### Core Process
スキルの核。エージェントが従う手順化されたワークフローです。曖昧な助言ではなく、具体的でアクション可能でなければなりません。

**良い例:** 「`npm test` を実行し、すべてのテストがパスすることを確認する」
**悪い例:** 「テストが動くことを確認する」

### Common Rationalizations
よく出来たスキルの最も際立った特徴です。これはエージェントが重要なステップをスキップするために使う言い訳と、それへの反論のペアです。これによってエージェントがプロセスから抜け出す正当化を防ぎます。

エージェントが「テストは後で追加します」「これは簡単だから仕様書は省略します」と言った場面をすべて思い出して、事実に基づく反論とともにここに入れましょう。

### Red Flags
スキルが破られている観察可能なサイン。コードレビューや自己監視時に有用です。

### Verification
完了条件。スキルのプロセスが完了したことをエージェントが確認するためのチェックリストです。各チェックボックスには、証拠（テスト出力、ビルド結果、スクリーンショットなど）による検証可能性が必要です。

## 補助ファイル

補助ファイルを作るのは以下のときだけ:
- 参照資料が 100 行を超えるとき（メインの SKILL.md を集中させるため）
- コードツールやスクリプトが必要なとき
- チェックリストが別ファイルを正当化するほど長いとき

50 行未満のパターンや原則はインラインのままにしましょう。

## 書き方の原則

1. **知識よりプロセス。** スキルはワークフローであり、参考書ではありません。事実ではなく手順を。
2. **一般より具体。** 「`npm test` を実行」は「テストを検証」より優れています。
3. **仮定より証拠。** すべての検証チェックボックスには証拠が必要です。
4. **反・合理化。** スキップされうるステップには Rationalizations テーブルに反論が必要です。
5. **段階的開示。** メインの SKILL.md はエントリーポイント。補助ファイルは必要なときだけロードされます。
6. **トークン意識。** すべてのセクションはその存在を正当化しなければなりません。削除してもエージェントの動作が変わらないなら削除しましょう。

## 命名規約

- スキルディレクトリ: `lowercase-hyphen-separated`
- スキルファイル: `SKILL.md`（常に大文字）
- 補助ファイル: `lowercase-hyphen-separated.md`
- References: プロジェクトルートの `references/` に置く（スキルディレクトリ内には置かない）

## スキル間の参照

他のスキルは名前で参照します。

```markdown
テストを書くときは `test-driven-development` スキルに従う。
ビルドが壊れたら `debugging-and-error-recovery` スキルを使う。
```

スキル間でコンテンツを複製しないでください — 参照とリンクで済ませましょう。
