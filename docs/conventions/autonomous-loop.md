# 自律開発ループ (Loop Engineering)

Claude Code を一定間隔で起動し、**1 サイクル = 1 機能 = 1 コミット**で Aidea を育てる運用のルール。
無人で回すため、守らせたいことは規約ではなく[品質ゲート](./quality-gates.md)（機械検査）で保証する。

**巻き戻せるから読まなくていい**が成立する条件を作るのが目的。
1 サイクル 1 コミットなら、気に入らないサイクルだけ `git revert` でき、
ブランチごと捨てれば main は無傷になる。最悪ケースで失うのは、そのブランチの作業ぶんだけになる。

## 適用範囲 — loop-safe 層に限る

Aidea は macOS GUI アプリで、**振る舞いの大半が画面表示と遷移**にある。
これらは自動テストで守れないため、無人ループの対象から外す。

| 区分 | 対象 | 無人ループ |
|---|---|---|
| **loop-safe** | View を持たない層: `Models/` / `Services/` のうち UI フレームワークに依存しないもの / `Sessions/` の純ロジック (パス解決・時刻計算・パーサ・レイアウト計算) | ✅ 可 |
| **human-only** | `Views/` / `Widgets/` の UI・SwiftUI/AppKit に依存する `Sessions/` / 端末描画・WebView・フォーカス制御 | ❌ 不可 |
| **human-only** | 大きな設計判断が要るもの、ADR を新設・変更するもの | ❌ 不可 |

判定は単純に「**そのファイルが SwiftUI / AppKit を import しているか**」を第一基準とする。
import していれば human-only。していなくても、UI の手触りを変える変更は human-only とする。

対象とする作業は GitHub Issues に `loop-safe` ラベルを付けて明示する。
**ラベルの無い issue には着手しない。**

## 1 サイクルの定義

1. **事前チェック**
   - 作業ブランチが `evolve/<連番>` であること。main にいたら最新化してブランチを切る
     (日付名にしない。人間が先に進んだとき、古い日付のブランチに commit してしまうため)
   - 前サイクルが途中で終わった形跡があれば、新しい作業に手を出さず続きから再開する
   - 人間の手作業らしき未コミット変更が混ざっていたら、**何もせず報告して終了する**
2. **1 件選ぶ** — `loop-safe` ラベルの issue から 1 件。実装中に別の改善点を見つけても**直さず**、
   issue に起票だけする
3. **specs を確認する** — 下記「[spec を変えるのか、spec に戻すのか](#spec-を変えるのかspec-に戻すのか)」で分岐する
4. **実装する** — 不具合修正なら[先に失敗するテストを書く](#不具合修正は失敗するテストから始める)
5. **ゲートを通す** — `scripts/gate.sh` が全通過するまで直す
6. **コミットする** — 1 サイクル 1 コミット。検証欄は `scripts/gate.sh` の出力をそのまま貼る
7. **issue を更新する** — 完了なら close、分割したなら子 issue を起票

### spec を変えるのか、spec に戻すのか

Aidea は specs-first だが、**すべての変更が spec 更新を伴うわけではない**。
着手前に 3 つのどれかを判定し、判定結果をコミットメッセージに書く。

| 状況 | spec の扱い | 進め方 |
|---|---|---|
| **spec に無い挙動を足す / 変える** | 実装前に spec を更新する | 更新した spec を先にコミットするか、同一コミットに含める |
| **spec に書かれた挙動に戻す (不具合修正)** | **変更しない** | コミットメッセージに「spec 変更なし (既存 spec に沿う挙動へ戻す修正)」と明記する |
| **spec に記述が無く、どちらとも言えない** | 判断しない | **人間の判断が要る**。issue に `blocked` を付けて理由を書き、サイクルを終える |

3 つ目を勝手に決めないこと。仕様の空白を埋めるのは設計判断であり、
[人間が担う領域](#人間が担う領域)に属する。

#### コミット時の specs 警告の扱い

Swift ファイルを変更して `docs/specs/` を変更しないままコミットすると、警告が出る。
これは**注意喚起であってゲートではない**ため、上の判定に従って扱う。

- 1 行目のケース → 警告が正しい。spec を更新してからコミットし直す
- 2 行目のケース → 警告は無視してよい。ただし**無視した理由をコミットメッセージに残す**
- 3 行目のケース → そもそもコミットしない (撤退する)

### 不具合修正は失敗するテストから始める

不具合を直すときは、**先にその不具合を捕まえるテストを書き、実際に失敗することを確認してから**
実装に移る。

- 失敗を確認しないまま直すと、「テストが本当にその不具合を捕まえているか」が不明のまま残る
- 修正後に通っただけでは、テストが最初から通っていた可能性を排除できない
- コミットメッセージに「修正前は失敗することを確認済み」と書けるのは、実際に確認したときだけ
  ([quality-gates.md](./quality-gates.md) の「自分が実行していない検証を実行したように書かない」と同じ原則)

## 撤退条件

無人運転で最悪なのは、同じエラーと延々格闘して費用だけ溶かすこと。

- **同じ原因で 2 回連続して失敗し、解決の目処が立たない場合**は、変更を `git stash` で退避し、
  該当 issue に `blocked` ラベルと理由を書き、そのことだけをコミットしてサイクルを終える
- 次のサイクルは別の issue に進むので、ループ全体は止まらない

### テストの失敗理由が読めないときの手順

`xcodebuild test` の標準出力には Swift Testing の失敗メッセージが出ない。
原因を読むには result bundle から取り出す:

```bash
xcodebuild test ... -resultBundlePath /tmp/r.xcresult
xcrun xcresulttool get test-results tests --path /tmp/r.xcresult --format json
```

`nodeType` が `Failure Message` のノードに、失敗した式と実際の値が入っている。
**失敗理由を読まずに修正を試みない。**

## 禁止事項

- main への直接 commit / push / merge (取り込みは人間がレビュー後に行う)
- 履歴改変 (`rebase -i` / force push / `reset --hard`) — `evolve` ブランチ上でも禁止
- ゲートが通っていない状態での commit / push
- `loop-safe` ラベルの無い issue への着手
- **human-only 層 (UI) の変更**
- ADR の新設・変更 (設計判断は人間が行う)
- 大規模リファクタリング (issue に起票して人間の判断を待つ)
- **実機確認したかのような記載** — 検証欄は `scripts/gate.sh` の出力のみ
  ([quality-gates.md](./quality-gates.md))

## Aidea 固有の注意

### 自己ホスティング

ループを回す Claude セッションは **Aidea 自身の中で動いている**。
Aidea を書き換えても、走行中のアプリは古いバイナリのままである。

- ループは**ビルドとテストまで**を行い、**アプリの再起動は人間が行う**
- 走行中の Aidea に影響を与えないため、ビルドは既定の DerivedData を共有する
  (再起動するまで挙動は変わらない)
- tmux 永続化により、Aidea を再起動してもループのセッションは生き残る

### 署名

ビルドは `CODE_SIGNING_ALLOWED=NO` で行う (証明書の期限に左右されないため)。
このビルド成果物は**配布・実機起動用ではない**。動作確認は人間が手元でビルドし直す。

## 人間が担う領域

ループが得意なのは、バックログの消化と機械的な正しさの担保。
以下は**気づくこと自体が人間の仕事**であり、ループには渡せない。

- 「使いにくい」「思ったのと違う」に気づいて言語化すること
- デザインの手触り、画面表示や遷移の良し悪し
- 何を作るか / 作らないかの判断
- 過去の設計判断 (ADR) をひっくり返すかどうか

気づいた不満を issue に書けばループが実装する。**気づくことはループにはできない。**
